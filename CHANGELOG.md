# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/) and the project uses [Semantic Versioning](https://semver.org/). The JSON data contract is versioned separately (`SCHEMA_VERSION`).

## [Unreleased]

### Changed (breaking, before any release)
- **Kotlin/Android package renamed from `dev.msgkit` to `io.github.pamoda2004.msgkit`** (and `dev.msgkit.android` to `io.github.pamoda2004.msgkit.android`), so the source package matches the Maven group `io.github.pamoda2004`. Update imports; ProGuard/R8 users get the new keep rule from the AAR automatically. Nothing had been published, so no released version is affected.
- **Event ids for WhatsApp exports and device (SMS/call-log) records are derived differently** (decision D1). They no longer depend on `utc_offset_minutes`, `date_order` or `default_country_code`: WhatsApp ids use the local wall-clock time exactly as written in the export, the sender as written and the body, plus an occurrence index so two identical messages in the same minute (for example two "ok") keep separate ids; device ids use the address or number as written. Re-importing the same chat with different settings, or from overlapping exports, now yields the same ids. Every id produced by earlier builds changes once; nothing had been published and no stored data exists, so no migration is provided. Facebook and webhook ids are unchanged.

### Added (retention and deletion, Phase 4, PR d; audit finding F13)
- **Delete everything about one person.** New trait `msgkit_core::store::EraseStore` (separate from `EventStore`, so nothing existing changes) with `erase_person(address, &EraseOptions)`, implemented by `MemoryStore` and `SqliteStore`. It erases the content of every held (not yet acknowledged) event in which the person is the sender, a recipient or a call participant, and returns a count; an address that matches nothing returns `0`, an empty one is `invalid_input`. **The address is normalised as at import:** phone-like input goes through `normalize_phone` with `EraseOptions::default_country_code`, anything else is trimmed and lower-cased (`store::address_key`), and stored addresses are compared the same way, so `0700000000`, `070 000 0000` and `+94700000000` erase the same person when the code is `94` (without it only international forms are recognised, and the docs say so). By default an erased event keeps its id, so a redelivered webhook is still a duplicate; `EraseOptions::drop_ids` forgets it too. Acknowledged events hold no content and their ids cannot be tied to a person, so they are not touched; they leave by age.
- **Retention.** New trait `msgkit_core::store::RetentionStore` (implemented by `SqliteStore` only: `msgkit-core` never reads a clock, so the memory store has none) with `expire_pending(older_than)`, which erases events that arrived that long ago and were never acknowledged (by arrival time, not the event's own timestamp), and `prune_acknowledged(older_than)`, which forgets old ids (the existing inherent method keeps working). **Exact retention of a kept id: 30 days (`DEFAULT_RETENTION`) from the moment the event was acknowledged, drained, erased or expired**, then removed by the next `prune_acknowledged`; the service runs it at start-up and every six hours, so an id can live up to six hours longer, and a library user must call it. Event ids are derived from sender and text (webhook ids from the platform id), so they are documented as pseudonymous personal data.
- **Service:** `MSGKIT_ID_RETENTION_DAYS` (default 30) and `MSGKIT_PENDING_MAX_AGE_DAYS` (default unset: nothing expires), whole days from 1 to 36500, a bad value stops the service at startup naming the variable only; `Config::{id_retention, pending_max_age}` with setters; `maintain_database` and `Maintenance` (the old `prune_database` stays). The periodic log line gives counts only.
- **Command line:** `msgkit store erase <db> (--address <a> | --address-stdin) [--default-country-code 94] [--drop-ids] [--compact]`. It prints only `erased N event(s)`; no message or error repeats the address.
- **`SqliteStore`:** `open_with` / `open_in_memory_with` and the `#[non_exhaustive]` `StoreOptions` (`secure_delete`), `checkpoint()` (truncate the write-ahead log) and `compact()` (`VACUUM`). Every deletion (erase, expire, prune) ends with a checkpoint. No HTTP endpoint yet (own PR, token required, address only in the JSON body).
- **Documented:** a production database must not live in a cloud-synced folder (OneDrive, Google Drive, Dropbox); what erasure cannot reach (backups, snapshots, sync copies, flash wear levelling); the threat model and privacy pages are updated.
- **Tests:** `store::conformance::run_erase` (run against both stores: five spellings of one number, with and without the country code, names, recipients, calls, unmatched address, empty address, `drop_ids`), the bytes of the database file and its `-wal` file after an erase and after an acknowledge (the text is present before and gone after), the retention clock of an erased id (kept at 29 days, removed at 31), `expire_pending` by arrival time, the upgrade of a version 1 database (also four threads opening one at once), service variables and a maintenance pass, and the command line.

### Changed (SQLite store, Phase 4, PR d: behaviour changes)
- **`secure_delete` is on by default** for connections opened by `SqliteStore`: deleted content is overwritten with zeros instead of left in free space. Deletes and updates are slightly slower. `StoreOptions::with_secure_delete(false)` switches it off. The setting belongs to a connection, so another process that opens the same file without it does not overwrite.
- **Database layout 1 to 2.** A new column `received_at` (seconds since the epoch of the insert) lets `expire_pending` work by arrival time. A version 1 database is upgraded in place when opened, in one transaction; rows already held are stamped with the upgrade time. **An older msgkit refuses a version 2 database** ("database layout version 2 is newer than this library supports"), so downgrading needs a copy made before the upgrade. No JSON schema, C ABI, binding or HTTP API changes.
- New Rust items are additive (`cargo semver-checks` reports no required update). `msgkit-cli` now depends on `msgkit-store-sqlite`.

### Added (redaction, Phase 4)
- **New optional crate `msgkit-redact`** (Rust only, additive; nothing else depends on it): best-effort masking of email addresses, phone numbers (international and Sri Lankan national), Sri Lankan NIC numbers (old 9 digits and `V` or `X`, new 12 digits), card numbers (Luhn and a known network prefix), IBANs (mod 97) and bank account numbers (a digit run after a keyword such as "account"), in text and in events. `Redactor::{redact_text, detect, redact_event, redact_report}`; masks are typed placeholders (`[PHONE]`, default), `KeepLast(n)` (`[CARD *1111]`) or keyed pseudonyms (`[PHONE:7f3a9c217f3a9c21]`, 8 bytes of HMAC-SHA256); `redact_event` drops `raw` by default; names are masked only from a list you give. Every match is confirmed by a validator and carries a confidence; amounts and quantities (prices in rupees, lakhs and millions, mileage, vehicle registration numbers, years, dates and times) are never masked, enforced by a negative corpus in the tests. Phone validation reuses `msgkit_core::phone::normalize_phone`. The Sri Lankan landline codes were checked against the TRCSL numbering plan (revised 22 October 2009; 29 geographic codes and the whole mobile level `07`); the plan is old, so extra codes are configurable. No NIC checksum is validated (no official algorithm could be verified). Documented, with its sources and its limits, in `docs/REDACTION.md`. Redacting is idempotent by construction (placeholders are never matched again, and the text is masked again until a pass finds nothing); the first CI fuzz run found two cases where it was not (a keyword reaching past the placeholder of its own number, and a number glued to an IBAN), both fixed and kept as regression tests and seeds. Tests: per-rule, negative corpus, masking, events, property tests (also run with 250,000 cases per property) and a fuzz target (`fuzz/fuzz_targets/redact.rs`). **Backlog:** a `redact` operation in the Python, Node.js and Kotlin packages and the HTTP service; Sinhala and Tamil account keywords once real samples exist (D6).
- **CI:** the `Rust public API (semver)` step excludes `msgkit-redact` (`--exclude msgkit-redact`), because a crate that is newer than the baseline tag has nothing to compare with and `cargo semver-checks` fails for it; no other crate and no other check changed, and the crate joins when the baseline moves to the first release (backlog: remove the exclusion then; msgkit-core, -ffi, -service, -store-sqlite and -wasm are still checked, and the command-line crate has no library API to check).

### Changed (HTTP service, Phase 4: two behaviour changes)
- **The service refuses to start on a non-loopback address without a token.** Before, `MSGKIT_BIND` set to anything but `127.0.0.1` or `::1` (for example `0.0.0.0:8080` in a container) with `MSGKIT_API_TOKEN` unset only logged a warning, and `/v1/*` was open to anyone who could reach the port. Now the process exits at startup with `refusing to listen on <address>: ... Set MSGKIT_API_TOKEN ... (for example `openssl rand -hex 32`)`. There is no override. **Affected:** any deployment that binds a non-loopback address without a token (including a Docker container that binds `0.0.0.0`). **Not affected:** loopback with or without a token, and any address with a token. Docker example and token generation in `docs/API.md` ("Securing the service").
- **Without a token, `/v1/*` refuses a `Host` header that is not the machine's own name** (a defence against DNS rebinding). `localhost`, `*.localhost`, loopback addresses (any port, any case) and the entries of the new `MSGKIT_ALLOWED_HOSTS` are accepted; anything else gets `403` with the new code `host_not_allowed`. **Affected:** a tokenless service reached under another name, for example through a reverse proxy on the same machine that forwards `Host: msgkit.example.com` (list the name in `MSGKIT_ALLOWED_HOSTS`, or set a token), or an embedding application that calls `router()` with another host. **Not affected:** requests without a `Host` header, `/healthz`, `/webhooks/*` (authenticated by signature; Meta sends your public name), and every request to a service that has `MSGKIT_API_TOKEN` set (the token is the defence; the host is not checked).

### Added (HTTP service, Phase 4)
- **New HTTP-only error code `host_not_allowed`** (403), additive: listed in `docs/ERRORS.md`, `openapi.yaml` (response `HostNotAllowed` on every `/v1/*` operation) and `msgkit_core::error::codes::ALL`. No existing code changed meaning. The text does not repeat the host.
- **`MSGKIT_ALLOWED_HOSTS`** (comma-separated host names, no scheme, path or wildcard; a port is ignored) and `Config::with_allowed_hosts`; a bad entry stops the service at startup, naming the variable only. New Rust items: `msgkit_service::check_bind` and `Config::allowed_hosts`. `Config` is already `#[non_exhaustive]`, so this is not breaking.

### Fixed (CI)
- **The coverage job no longer fails at random.** `tests/purity.rs` checks the whole workspace's dependency graph with `cargo tree --offline`, but the coverage job builds only `msgkit-core`, so the other crates' dependencies (for example `anstream`, used by the command line) were present only when the build cache happened to hold them; without them the test failed with "failed to download". The job now runs `cargo fetch --locked` first. No gate, job name or required check changed, and the test is unchanged. The other jobs that run the test (`Rust tests` on three systems, and the weekly latest-stable canary) run `cargo test --workspace`, which downloads everything already; the MSRV job only compiles the tests.

### Added (input limits and WebAssembly boundary, Phase 4, audit findings F02 and F11)
- **Input limits.** Every import now checks its input against `limits` and fails with `limit_exceeded` (a library error code now, not only an HTTP one) before parsing; nothing is truncated. **Defaults, as in the code (`msgkit_core::limits`): `max_input_bytes` 33554432 (32 MiB), `max_line_bytes` 262144 (256 KiB), `max_messages` 1000000, `max_json_depth` 32.** An absent or `null` limit has its default; a limit is a number of at least 1; **`0` is refused with `invalid_input`** (it would read as "allow nothing" and must never switch protection off); the one explicit opt-out is `"unlimited": true` (`Limits::unlimited()`, `--no-limits`, `MSGKIT_NO_LIMITS=true`). `limits` is an option of `parse_whatsapp_export`, `parse_facebook_export` and `normalize_device`, a top-level field of the two webhook operations, a typed option in the Node.js, Python and Kotlin packages (`limits=` keyword in Python, a `limits` argument on the webhook functions), and `Limits` in Rust. Details in `docs/API.md` ("Input limits"). **JSON schema 1.1.0 to 1.2.0, additive** (a new optional `limits` option and a `Limits` definition; the generated types gain `Limits`, nothing else changes). New conformance cases `limit_*` (12) run in every binding and over HTTP.
- **Newly rejected, by default** (accepted before): text or a JSON document over 32 MiB through the library, bindings and command line (the HTTP service refused over 64 MiB already, see below); a WhatsApp export line over 256 KiB; more than 1,000,000 messages, calls and notices in one import; JSON nested deeper than 32 levels (any depth up to serde_json's 128 was accepted). No file, fixture, conformance case or fuzz seed of this repository is affected (`crates/msgkit-core/tests/limits.rs::the_defaults_accept_every_fixture_conformance_input_and_fuzz_seed` checks all of them). Pass larger `limits` (or `unlimited`) to keep the old behaviour.
- **Changed (HTTP service): the default import body limit is 32 MiB, down from 64 MiB**, to match the library. An operator sets `MSGKIT_MAX_INPUT_BYTES`, `MSGKIT_MAX_LINE_BYTES`, `MSGKIT_MAX_MESSAGES` and `MSGKIT_MAX_JSON_DEPTH` (whole numbers of at least 1) or `MSGKIT_NO_LIMITS=true` to change them; a bad value stops the service at startup (`Config::try_from_env`, used by the binary; `Config::from_env` keeps its signature and leaves the limits at their defaults). A request body between 32 and 64 MiB that was accepted before now gets the 413 `limit_exceeded` JSON error. Webhooks stay at 2 MiB (or the body limit, if lower). **A client cannot change any limit** (`crates/msgkit-service/tests/limits.rs::a_client_cannot_lower_raise_or_disable_a_limit_in_any_way` and `a_request_cannot_raise_a_limit`): a `limits` query parameter is refused with `invalid_input`; `limits` or `options` inside a body, loose `max_*` parameters and headers are ignored.
- **Command line:** `--max-input-bytes`, `--max-line-bytes`, `--max-messages`, `--max-json-depth` (each at least 1, applied per file) and `--no-limits`; `msgkit device` now reports a limit as an error (it used to go through the infallible path and would have shown only a warning).
- **WebAssembly: the length-trust fix** (F11). `msgkit_dealloc` no longer trusts its length argument: the module records every buffer it hands out, frees with the recorded length, and ignores a pointer that is not the start of a live buffer (a wrong length or a double free used to be undefined behaviour inside the sandbox). `msgkit_call` answers `invalid_input` when an argument range is not inside a live buffer, and `msgkit_alloc` returns 0 for a request over 512 MiB (the Node.js package raises `limit_exceeded`). Exported function signatures are unchanged. Hosts that follow the documented protocol (allocate with `msgkit_alloc`, free what you got) are unaffected; a host that passed memory not allocated by `msgkit_alloc` as an argument must change. Tests (`crates/msgkit-wasm/src/lib.rs`): `dealloc_ignores_a_wrong_length`, `dealloc_ignores_a_repeated_or_foreign_pointer`, `dealloc_ignores_an_interior_pointer_of_a_live_buffer`, `call_refuses_ranges_outside_live_buffers`, `alloc_over_the_cap_returns_null`, `an_over_limit_input_is_limit_exceeded_through_the_module`.
- **New Rust items:** `msgkit_core::limits::{Limits, DEFAULT_MAX_*}` with `with_max_*` setters, `Limits::unlimited()` and `validate()`; `with_limits` on the three options structs; `webhook::normalize_whatsapp_with_limits` and `normalize_messenger_with_limits`; `device::try_normalize`. The infallible `whatsapp_export::parse` and `device::normalize` return no events and one warning when over a limit.

### Breaking (Rust API only, Phase 4)
- **`msgkit_core::Error` is now `#[non_exhaustive]` and has a new variant, `LimitExceeded(String)`** (code `limit_exceeded`). A `match` on `Error` outside `msgkit-core` needs a catch-all arm, or can use `Error::code()`. Within 0.2.0, which is not released.
- **`msgkit_service::Config` has a new public field (`limits`) and is now `#[non_exhaustive]`**, so settings added later are not breaking. Outside the crate it cannot be built with a struct literal; start from `Config::default()` or `Config::from_env()` and chain the new `with_whatsapp`, `with_messenger`, `with_api_token`, `with_db_path` and `with_limits` setters, or assign fields. `AppState::new` now also refuses a `0` limit.
- **The three options structs gained a public `limits` field.** They were already `#[non_exhaustive]`, so this is not breaking.
- No JSON, schema, C ABI, Python, Node.js, Kotlin or HTTP API is broken: every addition is optional with a default (the behaviour changes above are listed separately).

Also records why `verify_signature` returns `{"valid": false}` instead of an error (`docs/ERRORS.md`, audit finding F10). Documentation only; no behaviour changed.

### Added (API and schema stability, Phase 3)
- **Weekly mutation-testing workflow** (`.github/workflows/mutation.yml`, also runnable on demand): `cargo mutants` on `msgkit-core` with a pinned `cargo-mutants`, about 35 minutes. It is not a required check; it fails when a mutant survives and uploads the results as an artifact. The last full run caught all 216 viable mutants.
- **Public API surface and stability levels** (`docs/API_SURFACE.md`): lists what the Rust crates, the C and WebAssembly ABIs, and the Python, Node.js, Kotlin, HTTP and command-line interfaces expose, marks each item stable or unstable, and states the compatibility rules for each level. Documentation only; no API changed. `docs/API.md` now lists `storage_error` among the error codes (it was missing).
- **Schema policy** (`docs/SCHEMA_POLICY.md`): the schema has its own version (`SCHEMA_VERSION`); within 1.x it changes only additively, removals need a new major version (after a deprecation period of at least one minor release), and readers must accept older minor versions and tolerate newer ones. Every schema file now carries `x-msgkit-schema-version` (a metadata key that readers ignore; the data contract is unchanged and `SCHEMA_VERSION` stays `1.0.0`). `scripts/schema_compat.py` now also fails CI when an additive schema change lacks a minor `SCHEMA_VERSION` bump, when the version goes backwards, or when a file's marker disagrees with `SCHEMA_VERSION`.
- **Data types for TypeScript, Python and Kotlin are now generated from `schema/`** (`scripts/generate_types.py`, standard library only) instead of being written by hand. The generated code sits between `<generated types ...>` markers in `packages/node/src/index.d.ts`, `packages/python/src/msgkit/types.py` and `Models.kt`; a new required CI job, "Generated types match the schema", fails when they disagree with the schema. Names, field order, optionality and defaults are unchanged, and runtime behaviour is unchanged. The differences, all additive or widening:
  - TypeScript: new exported type `DateOrder` (`'auto' | 'dmy' | 'mdy'`); `WhatsAppExportOptions.date_order` now uses it (structurally identical to the inline union before).
  - Python: new `TypedDict`s `WhatsAppExportOptions`, `FacebookExportOptions` and `DeviceOptions` in `msgkit.types`.
  - Python: four input fields widened from `str` to `Optional[str]` to align the types with the schema, which allows `null` there: `RawSms.id`, `RawSms.thread_id`, `RawCall.id` and `RawCall.name`. Callers that pass strings are unaffected; only code that reads one of these fields and assumes `str` needs a `None` check under mypy.
  - Kotlin: none (`VersionInfo` moved to the end of the file).
  - Doc comments now come from the Rust doc comments; five hand-written comments were moved into the Rust docs, and the example phone numbers in them are now obviously fictional (`+94700000000`, `0700000000`).

### Changed (tests and fixtures only, Phase 3)
- **Example phone numbers are now obviously fictional** (audit finding F22). The Sri Lankan mobile number that tests, fixtures, conformance cases, the fuzz corpus and docs used (in its international, national, bare and spaced or hyphenated forms) is replaced everywhere by `+94700000000` / `0700000000`. Production code is unchanged. Because event ids are derived from the sender text, the expected ids of 10 events in 3 conformance cases changed (`device_batch`, `ids_phone_senders_country_94`, `ids_phone_senders_no_country_code`); a fourth case (`whatsapp_webhook`) changed only in text. Nothing else in any expected output differs.

### Changed (HTTP service, Phase 3)
- **A 413 (request body too large) on the text import and webhook POST endpoints is now a JSON error.** The status is unchanged. Before, the body was axum's plain text (`Content-Type: text/plain; charset=utf-8`):
  ```
  Failed to buffer the request body: length limit exceeded
  ```
  Now it is the same JSON as every other error (`Content-Type: application/json`):
  ```json
  {"error": "the request body is too large", "code": "limit_exceeded"}
  ```
  Affected: `POST /v1/import/whatsapp-export` (over 64 MiB) and `POST /webhooks/whatsapp` and `/webhooks/messenger` (over 2 MiB). The JSON endpoints already answered 413 with JSON and keep their text (`the request body could not be read (too large?)`), now with `"code": "limit_exceeded"` added. Clients that read the 413 body as text and matched the old sentence need to read `code` instead.

### Added (IANA time zones, Phase 3, decision D7)
- **Optional `time_zone` for WhatsApp exports** (for example `Asia/Colombo`), next to `utc_offset_minutes`: an option of `parse_whatsapp_export` in every binding (Python keyword `time_zone`, Node and Kotlin through the generated option types), a query parameter of `POST /v1/import/whatsapp-export` and the `--time-zone` flag of the command line. It follows the zone's daylight-saving rules and history. **Additive:** without it nothing changes (all 54 earlier conformance cases are byte-identical), `time_zone` wins when both are given, and **event ids never depend on it**. Names are exact and case-sensitive IANA names of the bundled database (aliases such as `Asia/Calcutta` work; `asia/colombo`, `+05:30`, `IST` and the empty string do not); anything else is `invalid_input` and the name is not repeated. A time in a repeated period (clocks back) uses its first occurrence, a time in a skipped period (clocks forward) moves forward by the gap, and one warning counts both and quotes nothing.
- **The time-zone database is bundled in the binary** (`jiff =0.2.38` and `jiff-tzdb =0.1.9`, default features off, `tzdb-bundle-always` on; IANA tzdata 2026e), so a name gives the same UTC instant in every binding on every platform. `msgkit-core` still reads no files, no environment and no clock: `crates/msgkit-core/tests/purity.rs` fails if source code touches them or if any OS time-zone feature of `jiff` is enabled, and a decoy `TZDIR` shows that OS files are ignored.
- **Tzdata update policy** (`CONTRIBUTING.md`, "Time-zone data"): a `jiff` or `jiff-tzdb` bump is reviewed as a behaviour change; its CHANGELOG entry names the old and new tzdata versions and the zones whose rules changed (found with `cargo run --release -p msgkit-core --example tz_fingerprint`); Dependabot opens these bumps as separate pull requests; `crates/msgkit-core/tests/tzdata_pin.rs` fails until the reviewed version is recorded.
- **`version` now also reports `tzdata_version`** (the bundled tzdata release; new field in `VersionInfo` of the Node, Python and Kotlin types). New Rust items: `whatsapp_export::try_parse` (like `parse`, but an unknown zone is `Error::InvalidInput`; `parse` warns and keeps `utc_offset_minutes`) and `msgkit_core::tzdata_version()`.
- **`SCHEMA_VERSION` is now 1.1.0** (a new optional property, `WhatsAppExportOptions.time_zone`; additive). The generated TypeScript, Python and Kotlin types and `openapi.yaml` follow.
- 12 conformance cases (`conformance/cases/tz_*`: Asia/Colombo including its 1996 and 2006 changes, New York and London gaps and folds, Lord Howe's 30-minute change, an alias, the zone replacing the offset, and four rejected names), in all five runners; the fuzz target and corpus replay now vary the zone; property tests for ids and for never panicking or repeating a zone name.
- CI prints package sizes (Python wheel per platform, npm package and WASM, Android libraries and AAR) in the job logs and summaries, so dependency changes can be measured.
- **Size cost of the bundled time-zone data, measured in CI (bytes, before to after):** Python wheel Linux x86_64 872,569 to 982,240 (+12.6%), macOS universal2 735,171 to 843,151 (+14.7%), Windows 756,622 to 865,018 (+14.3%); npm tarball 489,465 to 586,365 (+19.8%) with the WASM 1,472,815 to 1,791,585; Android AAR 3,263,142 to 3,696,400 (+13.3%), the native libraries growing by 292,592 to 340,296 each.

### Breaking (Rust API only, Phase 3)
- **`WhatsAppExportOptions` has a new public field, `time_zone`** (see "IANA time zones" above). The struct has only public fields, so Rust code that builds it by listing every field, without `..Default::default()`, no longer compiles until it adds `time_zone: None`. `cargo-semver-checks` reports it as `constructible_struct_adds_field`. **Not affected:** the JSON option (an absent `time_zone` is the same as before), the Python, Node.js, Kotlin, HTTP, command-line and C/WebAssembly interfaces, and Rust code that already uses `..Default::default()`.
- **`WhatsAppExportOptions`, `FacebookExportOptions` and `DeviceOptions` are now `#[non_exhaustive]`**, so options added in later versions are no longer breaking changes. Outside `msgkit-core` they cannot be built with a struct literal (not even with `..Default::default()`; error `E0639`). Start from `Default` and chain the new `with_*` setters, or assign fields:
  ```rust
  let opts = WhatsAppExportOptions::default()
      .with_self_name("Alice")
      .with_date_order(DateOrder::Dmy)
      .with_time_zone("Asia/Colombo");
  // or: let mut opts = WhatsAppExportOptions::default(); opts.utc_offset_minutes = 330;
  ```
  The setters are `with_self_name`, `with_date_order`, `with_utc_offset_minutes`, `with_conversation_id`, `with_default_country_code` and `with_time_zone` (WhatsApp); `with_self_name` and `with_conversation_id` (Facebook); `with_own_number` and `with_default_country_code` (device). Reading fields and JSON (de)serialization are unchanged, and no binding is affected: Python, Node.js, Kotlin, HTTP, the command line and the C/WebAssembly interfaces use JSON. Doc tests show both styles and check that a struct literal is rejected. The schema gains a one-line description for each of the three options objects (documentation only).
- **Every package moves from 0.1.0 to 0.2.0** (`msgkit-core` and the other crates, the Python wheel, the npm package, the Maven artifacts, `openapi.yaml`), the 0.x convention for a breaking change. Nothing had been published, so no released version is affected, and the semver gate is unchanged (it now compares 0.2.0 with the prototype baseline and passes).

### Added (error taxonomy, Phase 3)
- **One list of stable error codes** (`docs/ERRORS.md`, `msgkit_core::error::codes`) shared by the Rust core, the Python, Node.js and Kotlin packages, the C and WebAssembly ABIs and the HTTP service. **Every existing code keeps its meaning and is returned for exactly the same inputs as before** (`invalid_input`, `parse_error`, `unknown_op`, `storage_error`, `internal_error`): all 54 conformance cases pass unchanged in the Rust, Python, Node.js, Kotlin and HTTP runners, and no expected file was edited.
- **HTTP error responses now carry a `code`** next to the unchanged `error` text and unchanged HTTP status: `{"error": "...", "code": "..."}`. Five codes are new and are returned only by the HTTP service, for situations that previously had only a status and a text: `limit_exceeded` (413), `unauthorized` (401, bearer token), `signature_invalid` (401, webhook signature), `verification_failed` (403, webhook handshake) and `not_configured` (503). The library operations return no new code; `verify_signature` still answers `{"valid": false}`.
- `openapi.yaml`: the `Error` schema gains `code`; POST operations document the 413 response.
- The HTTP conformance runner now also sends the failing import cases through the service and requires the same `code` as the library; `crates/msgkit-service/tests/error_codes.rs` pins the status, code and text of every HTTP error response; `crates/msgkit-core/tests/error_taxonomy.rs` keeps the code, the documentation and `openapi.yaml` in step and checks that every code's test or case exists.

### Added (testing depth, Phase 2)
- **Conformance suite** (`conformance/`): 54 language-independent cases (input files plus the expected canonical JSON response) that the Rust core, the Python wheel, the Node.js WebAssembly package, the Kotlin/JNA package and the HTTP service must reproduce byte for byte; CI fails on any difference. Covers day/month ambiguity, 12/24-hour clocks, multi-line messages, media and system notices, deleted/edited messages, group chats, Facebook mojibake repair, emoji, Sinhala, Tamil and right-to-left text, very long messages, empty/truncated files, CRLF/LF/BOM variants, the id rules, signatures and error envelopes. See `conformance/README.md`.
- **Fuzz targets** (`fuzz/`, cargo-fuzz): the WhatsApp and Facebook parsers, the device normalizer, both webhook normalizers, the signature verifier and the JSON entry point, with a seed corpus taken from the conformance cases. CI fuzzes each target for 60 seconds on Linux; `crates/msgkit-core/tests/fuzz_corpus.rs` replays the corpus on every platform.
- **Property-based tests** (`proptest`, `crates/msgkit-core/tests/properties.rs`): no input panics a parser, the JSON entry point or the signature check; importing twice gives identical reports and a store de-duplicates; ids are unique and ignore the UTC offset and the default country code; timestamps are always UTC; error text never repeats the input; signatures round-trip and any change to body or signature is rejected.

### Fixed
- **System notices that contain a colon no longer become fake participants** (audit finding F03): `Alex changed the subject from "Team: A" to "B"` used to be parsed as a message from a sender called `Alex changed the subject from "Team`. Lines whose sender part is a known notice phrase or contains a quotation mark are notices.
- **Notices are no longer dropped silently** (F09, first part): a line without a sender that is neither a missed call nor a recognized English notice is counted in one warning (`N line(s) without a sender were ignored ...`), so exports in other languages show up instead of losing data unnoticed. The warning never quotes the line. Modelling deleted/edited messages as events stays with the lifecycle work in Phase 6.
- **Error messages no longer repeat the input** (audit finding F01). `serde_json` messages quoted the offending value (for example ``unknown variant `...` ``), and the HTTP service returned axum's default rejection text, which quoted request bodies. Core errors now keep only the category, a missing field's name and the position; the service answers malformed bodies and query strings with fixed texts. Guarded by `tests/error_redaction.rs`, an HTTP test and three conformance cases.

- Python: requests to the native library are serialized as compact JSON, so error messages that mention a column are identical in every binding.
